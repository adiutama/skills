## Harness

At the start, detect your harness with [harnesses.md § Detect](references/harnesses.md#detect), then read its glossary column. These terms mean exactly what that column says, everywhere in this skill and its references: **storage** (`<storage>` in paths) · **invoke** (`<invoke>` in commands) · **AI name** · **render**.

## Route

- PR URL or positive number → **1 — Collect**. `--services` names throwaway services for tests: a `services.md` record (its URLs and env lines are used) or a single connection URL.
- `submit [C1,W1] [--message <text>] [--accept-moved-head]` → follow [submit.md](references/submit.md), then stop.
- Missing or invalid target → ask once for a PR URL or number, then stop.
- Anything else → show the two forms above and stop.

Natural-language equivalents ("submit C1 and W1") count. A review never authorizes submission; only an explicit `submit` does.

**Session directory** `<S>` = `<storage>/pr-review/<owner>-<repo>-<number>/` (from the PR `url`, lowercased). It holds `NN.report.md` (NN = pass number), the review worktree, and probes. Name `<S>` in the handoff; later actions in this conversation reuse it.

## Writing

Every sentence a teammate who hasn't read the change understands on one reading. Keep facts, IDs, locations, URLs, and commands exact; never invent a fact to simplify; keep quoted and user-supplied text verbatim. Name the actor, one idea per sentence (aim 10–20 words), no process narration. Never turn a conditional risk into a certainty ("*can* charge twice"). Use the repo's domain language (`GLOSSARY.md` if present). Limits: finding comment ≤ 80 words, review message ≤ 60 words; exceed only when cutting would drop a condition.

**AI authorship.** Start the review message and every finding comment with `> ℹ️ This comment was generated by <AI name> on my behalf.` — your **AI name**, no version, once per message, also in saved drafts. Never claim the user wrote or verified it.

## 1 — Collect

Fetch metadata: `gh pr view <target> --json number,url,title,body,state,baseRefName,baseRefOid,headRefName,headRefOid,headRepository,files`. Fetch activity with `gh api --paginate`: reviews `repos/<o>/<r>/pulls/<n>/reviews` (time: `submitted_at`), PR comments `repos/<o>/<r>/issues/<n>/comments` and inline comments `repos/<o>/<r>/pulls/<n>/comments` (time: `updated_at`). Leave out bot authors (`user.type == "Bot"`).

Check out the exact head in an isolated worktree per [checkout.md](references/checkout.md); run every search, diff, and test there.

`<S>` already has a report: same head, same base, and no new activity (counts and newest time vs. its footer) → say it's unchanged, re-show the last handoff, stop. Otherwise this is a later pass: review the delta (`git diff <old-head>..<new-head>`, base movement, new activity), start from the last report, and reconcile each prior finding as `fixed | partial | not_done | regressed | obsolete`. A force-push that drops the old head → fresh full review.

State the PR, branch, and verified commit in one line.

## 2 — Orient

Treat the PR description as claims; follow the diff into callers, consumers, tests, contracts, config, and sibling paths. Build the visuals per [visuals.md](references/visuals.md), in text form:

| Visual | Answers | Required |
|---|---|---|
| **behavior diff** | what actually changed | always |
| **change map** | where do I start | always |
| **blast radius map** | what else it touches | always |
| **trigger path** | how it's reached | per blocking finding; in What changed only when the change sits deep and no finding shows the path |

Also note:

- **Intent vs. behavior** — claimed intent, then behavior confirmed in code or tests.
- **Evidence in the PR** — what the PR shows working. Evidence items stamped with a commit (`captured at <sha>`) older than the head are `stale`; say which. Missing evidence for risky behavior is a coverage gap, not a finding.
- **Merge danger** — **Door:** one-way (destructive, published contracts, data loss) or two-way (cheap rollback). An additive migration is two-way when a rollback leaves its tables unused, one-way when the change writes data the business must keep (e.g. payment details people entered). **Blast radius:** one word of your choice (`isolated`, `module`, `cross-module`, `platform`, …) plus the ramifications.
- **Review targets** — suspicions to test next. A suspicion is not a finding.

## 3 — Judge

Keep a finding only if it passes all four:

1. **Prove it.** Trace a reachable trigger through changed code to the consequence; record it as a trigger path for a blocking finding. Run a focused test when that resolves doubt (setup per [checkout.md § Running tests](references/checkout.md#running-tests)); the full suite only when no focused test covers the claim. Look for callers, guards, or tests that disprove it.
2. **Name the stakes.** Who or what is affected, and the concrete failure.
3. **Worth the interruption.** Drop preferences, cosmetic nits, speculative hardening, and test requests without a demonstrated risk.
4. **No repeats.** Merge same-cause findings; mark ones already raised on the PR `duplicate` with a link.

Status on the maps: ✅ checked, safe · ⚠️ not verified · ❌ broken. Only ❌ can become a finding; missing evidence, unverified concerns, and ⚠️ go to Coverage. Pin every finding on the maps.

**Severity.** `C1` critical (🛑): data loss, a security breach, or money moved wrongly — always blocking. `W1` warning (🟠): a realistic correctness, contract, or operational failure — blocking when it breaks a user-facing flow or a promise, else non-blocking. `N1` nit (⚪): never blocking. **Verdict:** `Request changes` if any finding blocks, else `Approve`.

**Placement.** A finding is `inline` when its line sits inside a diff hunk on its side (`RIGHT` new code, `LEFT` removed code, with the base file's line number); otherwise `body`, and its comment goes into the review message under "Other findings".

Write `<S>/NN.report.md` in this shape — decision first, findings before the maps, machine data in the footer:

## 4 — Hand off

Reply with the top of the report, visuals as your **render** says:

````markdown
<verdict box and three bullets>

<each pending finding: header, `path:line`, How it's reached, Comment to post>

<blast radius map>

**Report** — <S>/NN.report.md

### Proposed GitHub message
> <exact saved message>

### Next steps
- Submit: `<invoke> submit <pending IDs>` (optionally `--message "<text>"`)
- Or ask to revise the message or discuss a finding.
````

Never submit during the review. GitHub text (comments, message) stays prose — no rich visuals.
